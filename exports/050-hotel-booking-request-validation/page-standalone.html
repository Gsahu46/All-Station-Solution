The problem in real life

  1. Careful field checks

    Ghoomo's booking API checked every field: dates required and in the future, 1 to 10 adults, 0 to 10 children, a valid phone.

  2. Impossible bookings got through

    Support found requests with check-out before check-in, and 6 guests in a room for 2. Every field was valid on its own; nothing compared them.

  3. The fix

    Rules that look at the whole request, written as custom validators, run only once each field has passed, and answered with 422 instead of 400.

Valid parts do not make a valid whole. Some rules can only be checked by looking at two fields at once.

What are we building?

POST /hotel-bookings takes a booking request and either records it (201), says a field is broken (400), or says the fields do not add up (422), naming each field with its message. GET /hotel-bookings/{id} reads a recorded request back.

An everyday analogy

A hotel front desk. First the clerk checks the form is filled in properly: dates written as dates, a phone number with 10 digits. Only then do they check it makes sense: leaving after arriving, and a room big enough for everyone. A form with an empty box goes back for the box, not for a lecture on room sizes.

How it works in 4 steps

  1. Read the JSON; unreadable bodies and wrong types are 400.
  2. Field rules (the Default group) run on @Valid; any failure is 400, with every broken field named.
  3. Cross-field rules (the Consistency group) run next; any failure is 422, again naming fields.
  4. Record the request and answer 201 with its Location.
Check yourself: why not run all the rules at once?

A cross-field rule needs its fields. With check-in missing, "the stay is impossible" would be a confusing second error about the same mistake. Running the groups in order reports the missing date alone.

What this station is not

  • No availability. Whether the room is free is station 044.
  • No database. Hotels and requests live in memory.
  • No payment. A request record, not a confirmed booking.

Business problem

Ghoomo (a fictional travel app) accepted booking requests that could never be honoured, because each field was checked alone. Staff had to call guests back to sort them out.

Acceptance criteria

  1. Given 2 adults, a STANDARD room, 3 nights starting in 30 days, then 201, 3 nights, the phone as 10 digits, and GET returns it.
  2. Given check-out before check-in, or on the same day, then 422 naming checkOut.
  3. Given 4 adults and 2 children in a STANDARD room (sleeps 2), then 422 naming guests.
  4. Given check-in yesterday, over 365 days ahead, a stay over 30 nights, an unknown hotel or room type, then 422 naming the field.
  5. Given 0 adults, a phone of 5 digits, no room type, a date as 30-11-2026, 2.5 adults, or broken JSON, then 400.
  6. Given a missing check-in and 6 guests, then only the 400 for check-in.
  7. Given an unknown booking id, then 404.

Requirements

  • A rule about one field is a field constraint; a rule about several is a class-level constraint.
  • Field failures are 400, cross-field failures 422, both RFC 9457 problems with an errors map, field to message.
  • "Today" is today in India (Asia/Kolkata).
  • Room types are identifiers, normalised with Locale.ROOT.

Learning objectives

  • Write a custom ConstraintValidator for one field and for a whole object.
  • Use validation groups to order checks and to separate 400 from 422.
  • Give a validator Spring beans (a Clock, a catalogue).
  • Report every error on the field it concerns.

The trap

Plausible but wrong

Validating each field alone, so check-out before check-in passes.

The old request is kept in the tests as OldHotelBookingRequest: careful field rules, including @FutureOrPresent on both dates. The test runs the two bookings from the support tickets through the app's own validator: no violations at all. Then it sends the same bookings to the fixed API, which answers 422 and names the field.

While building, each part was undone once. Without @ValidStay, 3 tests turned red; without @RoomFitsGuests, 3; uppercasing room types with the server's locale instead of Locale.ROOT, 1 (the Turkish test). Moving the room rule into the Default group turned 5 red: it ran next to the field rules, so a missing date also produced a guests error, and too many guests became a 400.

/**
 * The first test written for this station: the two bookings from the support tickets, through the old request's

class FieldByFieldTrapTest extends ApiTest {

    @Autowired
    Validator validator;

    @Test
    void checkOutBeforeCheckInPassesEveryFieldRule() throws Exception {

    @Test

import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.ErrorResponseException;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

import java.net.URI;

@RestController
class BookingController {

    private final BookingDesk desk;

    BookingController(BookingDesk desk) {
        this.desk = desk;
    }

    /** @Valid runs the Default group only: a broken field stops here with 400, before any cross-field check. */
    @PostMapping("/hotel-bookings")

            p.setTitle("Booking not found");
            return new ErrorResponseException(HttpStatus.NOT_FOUND, p, null);
        });
    }
}

package com.ghoomo.bookings;

import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validator;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.stereotype.Service;
import org.springframework.web.ErrorResponseException;

import java.time.LocalDate;
import java.time.temporal.ChronoUnit;
import java.util.Map;
import java.util.Optional;
import java.util.Set;
import java.util.TreeMap;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

/** Checks that a booking request adds up, then records it. A request record only: no room is held, nothing is paid. */
@Service
class BookingDesk {

    record BookingView(long id, long hotelId, String hotelName, String roomType, LocalDate checkIn, LocalDate checkOut,
                       long nights, int adults, int children, String guestName, String phone, String status) {
    }

    private final Validator validator;
    private final HotelCatalog catalog;
    private final Map<Long, BookingView> bookings = new ConcurrentHashMap<>();   // shortcut: in memory, lost on restart; a real desk uses a table
    private final AtomicLong ids = new AtomicLong();

    BookingDesk(Validator validator, HotelCatalog catalog) {
        this.validator = validator;
        this.catalog = catalog;
    }

    /** Called after @Valid passed: every field is well-formed. Now the fields must agree with each other. */
    BookingView request(HotelBookingRequest r) {
        Set<ConstraintViolation<HotelBookingRequest>> violations = validator.validate(r, Consistency.class);
        if (!violations.isEmpty()) {
            Map<String, String> errors = new TreeMap<>();
            violations.forEach(v -> errors.merge(v.getPropertyPath().toString(), v.getMessage(), (a, b) -> a + "; " + b));
            ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_CONTENT, "Each field is valid, but together they are not a possible booking.");
            p.setTitle("Booking does not add up");
            p.setProperty("errors", errors);
            throw new ErrorResponseException(HttpStatus.UNPROCESSABLE_CONTENT, p, null);
        }
        HotelCatalog.Hotel hotel = catalog.find(r.hotelId()).orElseThrow();   // RoomFitsGuests checked it exists
        long id = ids.incrementAndGet();
        BookingView booking = new BookingView(id, hotel.id(), hotel.name(), HotelCatalog.roomType(r.roomType()), r.checkIn(), r.checkOut(),
                ChronoUnit.DAYS.between(r.checkIn(), r.checkOut()), r.adults(), r.childrenOrZero(), r.guestName().strip(),
                IndianMobile.Validator.digits(r.phone()), "REQUESTED");
        bookings.put(id, booking);
        return booking;
    }

    Optional<BookingView> find(long id) {
        return Optional.ofNullable(bookings.get(id));
    }
}

package com.ghoomo.bookings;

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

/**
 * Field rules (Default group) say each value is well-formed: 400 when broken. Class rules (Consistency group) say
 * the values make sense together: 422 when broken. They are separate so a missing date is never reported as an

@ValidStay(groups = Consistency.class)
@RoomFitsGuests(groups = Consistency.class)

        @NotNull Long hotelId,

        @NotNull LocalDate checkIn,
        @NotNull LocalDate checkOut,
        @NotNull @Min(1) @Max(10) Integer adults,
        @Min(0) @Max(10) Integer children,
        @NotBlank @Size(max = 80) String guestName,
        @NotBlank @IndianMobile String phone) {

    int childrenOrZero() {
        return children == null ? 0 : children;
    }
}

package com.ghoomo.bookings;

import jakarta.validation.Constraint;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import jakarta.validation.Payload;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.time.Clock;
import java.time.LocalDate;
import java.time.temporal.ChronoUnit;

/**
 * Cross-field: the stay makes sense as a whole. Check-in today or later and at most a year ahead; check-out after
 * check-in; at most 30 nights. Demo rules. A class-level constraint, because no single field can see the other.
 */
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = ValidStay.Validator.class)
@interface ValidStay {

    int MAX_NIGHTS = 30;
    int MAX_DAYS_AHEAD = 365;

    String message() default "the stay is not possible";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};

    /** Created by Spring, so it can be given the Clock like any other bean. */
    class Validator implements ConstraintValidator<ValidStay, HotelBookingRequest> {

        private final Clock clock;

        Validator(Clock clock) {
            this.clock = clock;
        }

        @Override
        public boolean isValid(HotelBookingRequest r, ConstraintValidatorContext context) {
            if (r.checkIn() == null || r.checkOut() == null) {
                return true;   // a missing date is a field error (400), reported by @NotNull
            }
            context.disableDefaultConstraintViolation();
            LocalDate today = LocalDate.now(clock);
            boolean ok = true;
            if (r.checkIn().isBefore(today)) {
                ok = fail(context, "checkIn", "must be today (" + today + ") or later");
            } else if (r.checkIn().isAfter(today.plusDays(MAX_DAYS_AHEAD))) {
                ok = fail(context, "checkIn", "bookings open at most " + MAX_DAYS_AHEAD + " days ahead");
            }
            if (!r.checkOut().isAfter(r.checkIn())) {
                ok = fail(context, "checkOut", "must be after checkIn: a stay is at least one night");
            } else if (ChronoUnit.DAYS.between(r.checkIn(), r.checkOut()) > MAX_NIGHTS) {
                ok = fail(context, "checkOut", "a stay is at most " + MAX_NIGHTS + " nights");
            }
            return ok;
        }

        static boolean fail(ConstraintValidatorContext context, String field, String message) {
            context.buildConstraintViolationWithTemplate(message).addPropertyNode(field).addConstraintViolation();
            return false;
        }

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = RoomFitsGuests.Validator.class)
@interface RoomFitsGuests {

    String message() default "the room does not fit the guests";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};

    /** Created by Spring, so it can use the catalogue bean. */
    class Validator implements ConstraintValidator<RoomFitsGuests, HotelBookingRequest> {

        Validator(HotelCatalog catalog) {
            this.catalog = catalog;

        @Override
        public boolean isValid(HotelBookingRequest r, ConstraintValidatorContext context) {
            if (r.hotelId() == null || r.roomType() == null || r.adults() == null) {
                return true;   // missing fields are reported by the Default group (400)
            }
            context.disableDefaultConstraintViolation();
            HotelCatalog.Hotel hotel = catalog.find(r.hotelId()).orElse(null);
            if (hotel == null) {
                return ValidStay.Validator.fail(context, "hotelId", "no hotel " + r.hotelId());
            }
            Integer sleeps = hotel.sleeps().get(HotelCatalog.roomType(r.roomType()));
            if (sleeps == null) {
                return ValidStay.Validator.fail(context, "roomType", hotel.name() + " has no such room type; it has " + new TreeSet<>(hotel.sleeps().keySet()));
            }
            int guests = r.adults() + r.childrenOrZero();
            if (guests > sleeps) {
                return ValidStay.Validator.fail(context, "guests", guests + " guests do not fit a " + HotelCatalog.roomType(r.roomType()) + " room, which sleeps " + sleeps);
            }
            return true;
        }

import jakarta.validation.Constraint;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import jakarta.validation.Payload;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

/** An Indian mobile number: 10 digits starting 6 to 9, optionally written with +91 or 0, spaces or hyphens. */
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = IndianMobile.Validator.class)
@interface IndianMobile {

    String message() default "must be a 10-digit Indian mobile number";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};

    class Validator implements ConstraintValidator<IndianMobile, String> {

        @Override
        public boolean isValid(String value, ConstraintValidatorContext context) {
            return value == null || digits(value) != null;   // null is @NotBlank's job, not this one's
        }

        /** The 10 digits, or null if this is not a mobile number. */
        static String digits(String value) {
            String d = value.replaceAll("[\\s-]", "");
            if (d.startsWith("+91")) {
                d = d.substring(3);
            } else if (d.length() == 11 && d.startsWith("0")) {
                d = d.substring(1);
            }
            return d.matches("[6-9][0-9]{9}") ? d : null;
        }
    }

package com.ghoomo.bookings;

import jakarta.validation.Constraint;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import jakarta.validation.Payload;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.util.Locale;

/** A GSTIN's shape and check character. A format check only: it does not prove the GSTIN is registered. */
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = Gstin.Validator.class)
@interface Gstin {

    String message() default "must be a 15-character GSTIN with a valid check character";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};

    class Validator implements ConstraintValidator<Gstin, String> {

        private static final String CHARS = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ";

        @Override
        public boolean isValid(String value, ConstraintValidatorContext context) {
            if (value == null) {
                return true;   // optional
            }
            String g = value.strip().toUpperCase(Locale.ROOT);
            return g.matches("[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z][1-9A-Z]Z[0-9A-Z]") && g.charAt(14) == checkCharacter(g);
        }

        /** The first 14 characters, weighted 1 and 2 alternately, base 36. */
        static char checkCharacter(String g) {
            int sum = 0;
            for (int i = 0; i < 14; i++) {
                int product = CHARS.indexOf(g.charAt(i)) * (i % 2 == 0 ? 1 : 2);
                sum += product / 36 + product % 36;
            }
            return CHARS.charAt((36 - sum % 36) % 36);
        }
    }
}

Interview takeaways

How do you validate that one field depends on another?

A class-level constraint: an annotation on the type and a ConstraintValidator that receives the whole object. Put the violation on the relevant field with addPropertyNode.

What are validation groups for?

To run subsets of rules at chosen moments: here, field rules first and cross-field rules only once the fields are valid. Groups can also differ between create and update.

400 or 422?

400 when the request is malformed or a field breaks its own rule; 422 when it is well-formed but describes something the server cannot do. Many APIs use 400 for both; the split helps clients know what to fix.

Can a ConstraintValidator use Spring beans?

Yes, when validation goes through Spring's Validator: Spring creates the validator and injects its constructor arguments, such as a Clock or a repository.

Why return true for null in a custom validator?

Each constraint checks one thing. Whether a value is required is @NotNull's job; returning false for null would report the same mistake twice.
