The problem in real life

  1. 900 lines, three channels

    Tijori's NotificationService wrote and sent SMS, email and push in one class. Every change was made in the same file.

  2. Two email changes broke SMS

    In March the email redesign lower-cased the address (customers without email now crashed before their SMS) and changed "Rs" to "₹" in the shared amount format (SMS lost its 160-character limit).

  3. The fix

    One small class per channel, each with its own wording and limits, behind a two-method interface; the service only decides which channels to use, and one channel's failure cannot stop another.

When three things change for different reasons, keep them in three places, so a change to one cannot break the others.

What are we building?

Internal systems post a notice (POST /notifications): a debit, a new-device login, a statement. The service decides which channels it goes to and answers what happened on each. Customers set which channels they want (PUT /customers/{id}/notification-preferences).

An everyday analogy

A bank branch with one clerk who writes every letter, SMS and phone call. Teach them a new letter format and they start writing SMS like letters. A branch with a letter desk, an SMS desk and a phone desk, and a manager who only says "send this to the SMS desk and the letter desk", can retrain one desk without the others noticing.

How it works in 4 steps

  1. A notice arrives: debit of ₹1,499 for Asha at BigBasket.
  2. The service asks the rule for that type and Asha's preferences: which channels?
  3. Each chosen channel writes its own text and records it; a channel with no address says UNREACHABLE.
  4. A channel that throws is marked FAILED; the others are unaffected.
Check yourself: why does the SMS say "Rs" while the email says "₹"?

"₹" is not in GSM-7. One such character turns the whole SMS into UCS-2, where one part holds 70 characters instead of 160, so the alert costs two or three parts. Email has no such limit. Only the SMS class needs to know this.

What this station is not

  • No real providers. Messages are recorded, not sent.
  • No retries or queue. Retrying failed channels is challenge 2.
  • No login. In a bank only internal systems may post notices.

Business problem

Tijori (a fictional digital bank) sends alerts by SMS, email and push from one large class. Each change for one channel risked the others, and in March two of them stopped debit alerts.

Acceptance criteria

  1. Given a ₹1,499 debit for Asha, then SMS, email and push are SENT, each in its own words; the SMS is GSM-7 and at most 160 characters.
  2. Given the same for Rohan (no email, no app), then the SMS is SENT, email UNREACHABLE, push SKIPPED.
  3. Given the email provider throws, then email is FAILED and SMS and push are SENT.
  4. Given Asha turns off email and push, then a statement notice goes by SMS only, a debit by SMS, and a new-device login still to all three.
  5. Given ₹1,23,45,678.90, then the SMS shows Indian grouping.
  6. Given a malformed body, 400; a debit without amount or an unknown customer, 422; preferences of an unknown customer, 404.

Requirements

  • One class per channel; the service depends only on the Channel interface.
  • One channel's failure never stops another.
  • Money in integer paise, shown in Indian grouping.
  • Addresses are masked in responses.

Learning objectives

  • Split a class by its reasons to change.
  • Depend on a small interface and let Spring inject every implementation.
  • Isolate failures between independent parts.
  • Tell useful structure from overkill.

The trap

Plausible but wrong

One class doing SMS, email and push, so one change breaks all three.

The old class is kept in the tests as OldNotificationService, with its two March changes. Both were made for email. The first lower-cases the email address before anything is sent: for Rohan, who has no email, it throws, and his debit alert never goes out by any channel. The second changed the shared amount format from "Rs" to "₹": the SMS now contains a character outside GSM-7 and is over 70 characters, so it is sent in parts. Through the fixed service, Rohan's SMS is SENT and Asha's SMS is GSM-7 within 160 characters.

While building, each part was undone once. Removing the per-channel try turned 1 test red (the email outage); "₹" in the SMS, 3; ignoring preferences, 1; western grouping, 2. Removing the email channel's "no address" check turned 1 red, and showed isolation working: the email channel threw, was marked FAILED instead of UNREACHABLE, and the SMS still went.

    void notify(Model.Customer c, Model.Notice n) {

            outbox.record(Model.ChannelName.PUSH, c.pushToken(), amount(n.amountPaise()) + " debited");

package com.tijori.notifications;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.ErrorResponseException;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

import java.time.Clock;
import java.time.LocalDate;
import java.util.Locale;

@RestController
class NotificationController {

    /** Merchant names as they appear on SMS: letters, digits, spaces and a few marks, at most 24. */
    record NewNotification(@NotNull Long customerId, @NotNull Model.NotificationType type,
                           @Min(1) @Max(10_000_000_000L) Long amountPaise, @Pattern(regexp = "[A-Za-z0-9 .&-]{1,24}") String merchant) {
    }

    record PreferencesBody(@NotNull Boolean sms, @NotNull Boolean email, @NotNull Boolean push) {
    }

    private final NotificationService notifications;
    private final Customers customers;
    private final Clock clock;

    NotificationController(NotificationService notifications, Customers customers, Clock clock) {
        this.notifications = notifications;
        this.customers = customers;
        this.clock = clock;
    }

    /** Demo: unprotected. In a bank only internal systems (payments, login) may call this, authenticated. */
    @PostMapping("/notifications")
    @ResponseStatus(HttpStatus.CREATED)
    NotificationService.Notification notify(@Valid @RequestBody NewNotification body) {
        Model.Customer customer = customers.find(body.customerId())
                .orElseThrow(() -> problem(HttpStatus.UNPROCESSABLE_CONTENT, "Unknown customer", "No customer " + body.customerId() + "."));
        if (body.type() == Model.NotificationType.DEBIT_ALERT && body.amountPaise() == null) {
            throw problem(HttpStatus.UNPROCESSABLE_CONTENT, "Amount missing", "A debit alert needs amountPaise.");
        }
        String merchant = body.merchant() == null ? null : body.merchant().strip().toUpperCase(Locale.ROOT);
        return notifications.send(customer, new Model.Notice(body.type(), body.amountPaise(), merchant, LocalDate.now(clock)));
    }

    @PutMapping("/customers/{id}/notification-preferences")
    Model.Preferences preferences(@PathVariable long id, @Valid @RequestBody PreferencesBody body) {
        customers.find(id).orElseThrow(() -> problem(HttpStatus.NOT_FOUND, "Customer not found", "No customer " + id + "."));
        Model.Preferences p = new Model.Preferences(body.sms(), body.email(), body.push());
        customers.setPreferences(id, p);
        return p;
    }

    static ErrorResponseException problem(HttpStatus status, String title, String detail) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(status, detail);
        pd.setTitle(title);
        return new ErrorResponseException(status, pd, null);
    }
}

src/main/java/com/tijori/notifications/NotificationService.java

Does
Picks channels by the type's rule and the preferences; asks each to deliver; isolates failures.
Why
Knows no wording and no provider: only the Channel interface.
Without it
One channel's crash stopping the rest.
  • Spring injects every Channel bean as a list: a new channel is a new class, not an edit here.
  • A RuntimeException from one channel becomes FAILED for that channel only, and is logged.
package com.tijori.notifications;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.atomic.AtomicLong;

/**
 * Decides which channels a notice goes to and asks each one to deliver it. It knows no wording, no address format
 * and no provider: it depends on the Channel interface, and Spring hands it every Channel bean there is.
 */
@Service
class NotificationService {

    private static final Logger log = LoggerFactory.getLogger(NotificationService.class);

    record Notification(long id, long customerId, Model.NotificationType type, List<Model.Delivery> deliveries) {
    }

    private final List<Channel> channels;
    private final Customers customers;
    private final AtomicLong ids = new AtomicLong();

    NotificationService(List<Channel> channels, Customers customers) {
        this.channels = channels;
        this.customers = customers;
    }

    Notification send(Model.Customer customer, Model.Notice notice) {
        Model.Preferences prefs = customers.preferencesOf(customer.id());
        List<Model.Delivery> deliveries = new ArrayList<>();
        for (Channel channel : channels) {
            if (!notice.type().wants(channel.name(), prefs)) {
                deliveries.add(new Model.Delivery(channel.name(), Model.Status.SKIPPED, null, null));
                continue;
            }
            try {
                deliveries.add(channel.deliver(customer, notice));
            } catch (RuntimeException e) {
                // One channel failing must not stop the others: the SMS still goes when email is down.
                log.warn("{} delivery failed for customer {}", channel.name(), customer.id(), e);
                deliveries.add(new Model.Delivery(channel.name(), Model.Status.FAILED, null, null));
            }
        }
        deliveries.sort((a, b) -> a.channel().compareTo(b.channel()));
        return new Notification(ids.incrementAndGet(), customer.id(), notice.type(), deliveries);
    }
}

package com.tijori.notifications;

/**
 * The one thing the notification service needs from a channel. Each implementation owns its wording, its length
 * limits and its address; a change to one cannot reach the others. Small on purpose: two methods.
 */
interface Channel {

    Model.ChannelName name();

    /** Writes and records the message, or answers UNREACHABLE when the customer has no address on this channel. */
    Model.Delivery deliver(Model.Customer customer, Model.Notice notice);
}

import org.springframework.stereotype.Component;

import java.time.format.DateTimeFormatter;

/**
 * SMS: one part of 160 characters in the GSM-7 alphabet. "₹" is not in GSM-7: one ₹ makes the whole message UCS-2,
 * where a part holds only 70 characters. So SMS says "Rs", and only this class has to know that.
 */
@Component
class SmsChannel implements Channel {

    static final int MAX_LENGTH = 160;
    private static final DateTimeFormatter DATE = DateTimeFormatter.ofPattern("dd-MM-yy");

    private final Outbox outbox;

    SmsChannel(Outbox outbox) {
        this.outbox = outbox;
    }

    @Override
    public Model.ChannelName name() {
        return Model.ChannelName.SMS;
    }

    @Override
    public Model.Delivery deliver(Model.Customer c, Model.Notice n) {
        if (c.phone() == null) {
            return new Model.Delivery(name(), Model.Status.UNREACHABLE, null, null);
        }
        String text = switch (n.type()) {
            case DEBIT_ALERT -> "Tijori: Rs " + Rupees.format(n.amountPaise()) + " debited from a/c XX" + c.accountLast4()
                    + (n.merchant() == null ? "" : " at " + n.merchant()) + " on " + DATE.format(n.date()) + ". Not you? Call 1800-000-0000.";
            case NEW_DEVICE_LOGIN -> "Tijori: new login to your account on " + DATE.format(n.date()) + ". Not you? Call 1800-000-0000.";
            case STATEMENT_READY -> "Tijori: your statement for a/c XX" + c.accountLast4() + " is ready in the app.";
        };
        if (text.length() > MAX_LENGTH) {
            throw new IllegalStateException("SMS over " + MAX_LENGTH + " characters: " + text.length());
        }
        outbox.record(name(), c.phone(), text);
        return new Model.Delivery(name(), Model.Status.SENT, "******" + c.phone().substring(6), text);
    }
}

The shared plain types; the per-type channel rule lives on NotificationType.

package com.tijori.notifications;

import java.time.LocalDate;

/** The few plain types every part shares. No behaviour lives here. */
final class Model {

    private Model() {
    }

    enum ChannelName { SMS, EMAIL, PUSH }

    enum Status { SENT, SKIPPED, UNREACHABLE, FAILED }

    /**
     * Who gets what, by type. Demo rules: a debit alert always goes by SMS; a new-device login goes to every channel
     * we can reach; a statement notice follows the customer's preferences only.
     */
    enum NotificationType {
        DEBIT_ALERT, NEW_DEVICE_LOGIN, STATEMENT_READY;

        boolean wants(ChannelName channel, Preferences p) {
            return switch (this) {
                case NEW_DEVICE_LOGIN -> true;
                case DEBIT_ALERT -> channel == ChannelName.SMS || p.allows(channel);
                case STATEMENT_READY -> p.allows(channel);
            };
        }
    }

    record Preferences(boolean sms, boolean email, boolean push) {
        boolean allows(ChannelName channel) {
            return switch (channel) {
                case SMS -> sms;
                case EMAIL -> email;
                case PUSH -> push;
            };
        }
    }

    /** Any of phone, email and pushToken may be missing: not every customer has an app or an email address. */
    record Customer(long id, String name, String accountLast4, String phone, String email, String pushToken) {
    }

    /** What happened, without any channel's wording. Each channel writes its own text from this. */
    record Notice(NotificationType type, Long amountPaise, String merchant, LocalDate date) {
    }

    record Delivery(ChannelName channel, Status status, String to, String text) {
    }
}

src/main/java/com/tijori/notifications/Rupees.java

Indian grouping for paise, written by hand because DecimalFormat supports only one group size.

package com.tijori.notifications;

/**
 * Paise as Indian-grouped rupees: 12345678 paise is "1,23,456.78". Written by hand because java.text.DecimalFormat
 * supports a single group size, so its en-IN format prints 12,345,678.00 (checked while building this station).
 */
final class Rupees {

    private Rupees() {
    }

    static String format(long paise) {
        String rupees = Long.toString(paise / 100);
        StringBuilder grouped = new StringBuilder(rupees.substring(Math.max(0, rupees.length() - 3)));
        for (int end = rupees.length() - 3; end > 0; end -= 2) {
            grouped.insert(0, rupees.substring(Math.max(0, end - 2), end) + ",");
        }
        return grouped + "." + String.format("%02d", paise % 100);
    }
}

package com.tijori.notifications;

import java.time.LocalDate;

/** The few plain types every part shares. No behaviour lives here. */
final class Model {

    private Model() {
    }

    enum ChannelName { SMS, EMAIL, PUSH, WHATSAPP }

    enum Status { SENT, SKIPPED, UNREACHABLE, FAILED }

    /**
     * Who gets what, by type. Demo rules: a debit alert always goes by SMS; a new-device login goes to every channel
     * we can reach; a statement notice follows the customer's preferences only.
     */
    enum NotificationType {
        DEBIT_ALERT, NEW_DEVICE_LOGIN, STATEMENT_READY;

        boolean wants(ChannelName channel, Preferences p) {
            return switch (this) {
                case NEW_DEVICE_LOGIN -> true;
                case DEBIT_ALERT -> channel == ChannelName.SMS || p.allows(channel);
                case STATEMENT_READY -> p.allows(channel);
            };
        }
    }

    record Preferences(boolean sms, boolean email, boolean push, boolean whatsapp) {
        Preferences(boolean sms, boolean email, boolean push) {
            this(sms, email, push, false);   // WhatsApp is opt-in
        }

        boolean allows(ChannelName channel) {
            return switch (channel) {   // the compiler lists every place a new channel must be decided
                case SMS -> sms;
                case EMAIL -> email;
                case PUSH -> push;
                case WHATSAPP -> whatsapp;
            };
        }
    }

    /** Any of phone, email and pushToken may be missing: not every customer has an app or an email address. */
    record Customer(long id, String name, String accountLast4, String phone, String email, String pushToken) {
    }

    /** What happened, without any channel's wording. Each channel writes its own text from this. */
    record Notice(NotificationType type, Long amountPaise, String merchant, LocalDate date) {
    }

    record Delivery(ChannelName channel, Status status, String to, String text) {
    }
}

package com.tijori.notifications;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

/**
 * Decides which channels a notice goes to and asks each one to deliver it. It knows no wording, no address format
 * and no provider: it depends on the Channel interface, and Spring hands it every Channel bean there is.
 */
@Service
class NotificationService {

    private static final Logger log = LoggerFactory.getLogger(NotificationService.class);

    record Notification(long id, long customerId, Model.NotificationType type, List<Model.Delivery> deliveries) {
    }

    private final List<Channel> channels;
    private final Customers customers;
    private final AtomicLong ids = new AtomicLong();
    private final Map<Long, Sent> sent = new ConcurrentHashMap<>();   // shortcut: in memory; a real service keeps a table

    private record Sent(Model.Customer customer, Model.Notice notice, Notification notification) {
    }

    NotificationService(List<Channel> channels, Customers customers) {
        this.channels = channels;
        this.customers = customers;
    }

    Notification send(Model.Customer customer, Model.Notice notice) {
        Model.Preferences prefs = customers.preferencesOf(customer.id());
        List<Model.Delivery> deliveries = new ArrayList<>();
        for (Channel channel : channels) {
            if (!notice.type().wants(channel.name(), prefs)) {
                deliveries.add(new Model.Delivery(channel.name(), Model.Status.SKIPPED, null, null));
                continue;
            }
            try {
                deliveries.add(channel.deliver(customer, notice));
            } catch (RuntimeException e) {
                // One channel failing must not stop the others: the SMS still goes when email is down.
                log.warn("{} delivery failed for customer {}", channel.name(), customer.id(), e);
                deliveries.add(new Model.Delivery(channel.name(), Model.Status.FAILED, null, null));
            }
        }
        deliveries.sort((a, b) -> a.channel().compareTo(b.channel()));
        Notification n = new Notification(ids.incrementAndGet(), customer.id(), notice.type(), deliveries);
        sent.put(n.id(), new Sent(customer, notice, n));
        return n;
    }

    /** Delivers again only what FAILED; every other channel keeps its first result, so nobody gets a second SMS. */
    synchronized Notification retry(long id) {
        Sent s = sent.get(id);
        if (s == null) {
            throw NotificationController.problem(HttpStatus.NOT_FOUND, "Notification not found", "No notification " + id + ".");
        }
        if (s.notification().deliveries().stream().noneMatch(d -> d.status() == Model.Status.FAILED)) {
            throw NotificationController.problem(HttpStatus.CONFLICT, "Nothing to retry", "No delivery of notification " + id + " failed.");
        }
        List<Model.Delivery> deliveries = new ArrayList<>();
        for (Model.Delivery d : s.notification().deliveries()) {
            deliveries.add(d.status() != Model.Status.FAILED ? d : attempt(channelNamed(d.channel()), s.customer(), s.notice()));
        }
        Notification n = new Notification(id, s.customer().id(), s.notice().type(), deliveries);
        sent.put(id, new Sent(s.customer(), s.notice(), n));
        return n;
    }

    private Channel channelNamed(Model.ChannelName name) {
        return channels.stream().filter(c -> c.name() == name).findFirst().orElseThrow();
    }

    private Model.Delivery attempt(Channel channel, Model.Customer customer, Model.Notice notice) {
        try {
            return channel.deliver(customer, notice);
        } catch (RuntimeException e) {
            log.warn("{} delivery failed again for customer {}", channel.name(), customer.id(), e);
            return new Model.Delivery(channel.name(), Model.Status.FAILED, null, null);
        }
    }
}

Interview takeaways

What does the single responsibility principle mean in practice?

A class should have one reason to change. SMS limits, email layout and the who-gets-what rule change for different reasons, at different times, by different people, so they live in different classes.

What is dependency inversion here?

NotificationService depends on the Channel interface; the SMS and email classes depend on it too. Neither side depends on the other's details, so either can change alone.

How does Spring help?

Injecting List<Channel> gives every Channel bean. Adding a channel is one new class; the service does not change.

Why catch exceptions per channel?

Channels are independent. Without it, the first failure stops every later channel: an email outage would stop debit alerts by SMS.

When is an interface overkill?

When there is one implementation, it is unlikely to grow, and tests do not need a substitute. Extract it when the second implementation or a real test need arrives.
