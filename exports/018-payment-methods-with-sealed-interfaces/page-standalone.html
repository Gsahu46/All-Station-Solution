Level 1, about 5 minutes. Plain language: no code.

The problem in real life

  1. Paysetu adds wallets

    The payment class gets one more nullable field, walletMobile. Checkout works; the tests for checkout pass.

  2. The first wallet refund

    The refund code checks UPI, then card, then net banking, and returns nothing for anything else. Wallet refunds silently go nowhere, and support finds out from customers.

  3. The fix

    Model "one of four" as a sealed interface with a record per method, and handle them with switches that have no default. Adding a fifth method now stops the build at every place that forgot it.

Let the compiler keep the list of cases, so a new one cannot be forgotten quietly.

What are we building?

POST /payment-intents takes an order, an amount and exactly one payment method. It answers with what the payer does next (approve in a UPI app, enter an OTP, log in to the bank, confirm a wallet debit) and where a refund would go.

An everyday analogy

A paper form with a separate box for each way to pay, where you may fill in only one box. Nobody can tick "UPI" and also write a card number, and the clerk's checklist has a line for every box on the form.

How it works in 4 steps

  1. Read the type: "type": "UPI" picks the UPI record; other fields are refused.
  2. Validate that record's own fields: a UPI ID, a 4-letter bank code, a 10-digit mobile.
  3. Switch on the method for the next action; the compiler checks all four are handled.
  4. Switch again for the refund route, with the same guarantee.
Check yourself: why not keep the old class and add a test for wallet refunds?

That test catches wallets, once. The next method (say, pay later) needs someone to remember every place again. With a sealed interface and no default branch, the build itself fails at each place that does not handle the new method.

What this station is not

  • No real payment. Nothing contacts NPCI, a bank or a card network.
  • No card numbers. Only a token, the network and the last 4 digits; a full number is refused.
  • No storage. Challenge 1 adds it.

Business problem

Paysetu (a fictional payment gateway) has one Payment class with a nullable field for every method. Each new method means hunting for every if (vpa != null) … else if … chain. The refund chain was missed when wallets launched, so wallet refunds returned nothing. The class also accepts a payment that is UPI and card at once.

Acceptance criteria

  1. Given a UPI ID in any case, then it is stored lower-case and the payer is asked to approve in their UPI app.
  2. Given a card, then the response shows the network and last 4 digits, never the token.
  3. Given net banking at hdfc, then a redirect to the (simulated) HDFC login; at a bank that is not offered, 422.
  4. Given a wallet, then the refund route is the wallet, with the mobile number masked.
  5. Given a UPI method with card fields, an unknown or missing type, or a bad field, then 400.
  6. Given every permitted payment method, then it can arrive as JSON and has a next action and a refund route.

Requirements

  • One record per method; each has only its own fields. A switch over methods has no default.
  • Identifiers are normalised with Locale.ROOT: UPI IDs lower-case, bank codes upper-case.
  • Amounts are whole paise, ₹1 to ₹1,00,000 (a demo rule).
  • Secrets are write-only: the card token and wallet mobile are accepted, never returned in full.

Learning objectives

  • Model "exactly one of" data with a sealed interface and records.
  • Use switch pattern matching and record patterns, and explain exhaustiveness.
  • Read polymorphic JSON with a type field, and refuse fields that do not belong.
  • Write a test that covers every subtype without listing them.

The trap

Plausible but wrong

One class with nullable fields for every method, so a new method is silently missed.

The first test shows the old refund chain returning null for a wallet. The second shows the old class taking a UPI-and-card payment and picking whichever if comes first. The third shows the sealed model refunding the wallet and refusing the mixed body. While building, making JSON lenient, echoing the token, and unregistering wallets each turned tests red.

package com.paysetu.payments;

import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

/** The first test written for this station: it reproduces the bugs before the fix. */
class ForgottenWalletTrapTest extends ApiTest {

    /** The "before" model: one class, a nullable field per method. Kept only in tests. */
    record OldPayment(String vpa, String cardLast4, String bankCode, String walletMobile) {
    }

    /** The "before" refund path. It compiles, and nothing says wallets are missing. */
    static String oldRefundRoute(OldPayment p) {
        if (p.vpa() != null) {
            return "UPI " + p.vpa();
        } else if (p.cardLast4() != null) {
            return "card " + p.cardLast4();
        } else if (p.bankCode() != null) {
            return "bank " + p.bankCode();
        }
        return null;   // wallets were added later; nobody came back here
    }

    @Test
    void theOldRefundPathSilentlyForgetsWallets() {
        assertThat(oldRefundRoute(new OldPayment(null, null, null, "9876543210"))).isNull();
    }

    @Test
    void theOldClassAcceptsAPaymentThatIsTwoMethodsAtOnce() {
        // UPI and a card in one payment: the old code just picks whichever if comes first.
        assertThat(oldRefundRoute(new OldPayment("asha@okaxis", "4242", null, null))).isEqualTo("UPI asha@okaxis");
    }

    @Test
    void theSealedModelRefundsWalletsAndRefusesMixedMethods() throws Exception {
        intent("{\"type\":\"WALLET\",\"mobile\":\"9876543210\"}")
                .andExpect(status().isCreated())
                .andExpect(jsonPath("$.refundRoute").value("Back to the Paysetu wallet of 98******10."));
        intent("{\"type\":\"UPI\",\"vpa\":\"asha@okaxis\",\"last4\":\"4242\"}").andExpect(status().isBadRequest());
    }
}

package com.paysetu.payments;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.ErrorResponseException;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

import java.util.Set;
import java.util.UUID;

@RestController
class PaymentIntentController {

    /** Banks offered for net banking in this demo. */
    static final Set<String> BANKS = Set.of("HDFC", "ICIC", "SBIN", "UTIB", "KKBK");

    record IntentRequest(@NotNull @Pattern(regexp = "[A-Za-z0-9_-]{1,40}") String orderId,
                         @NotNull @Min(100) @Max(value = 10_000_000, message = "must be at most Rs 1,00,000 (a demo rule)") Long amountPaise,
                         @NotNull @Valid PaymentMethod method) {
    }

    record Intent(String id, String orderId, long amountPaise, String status, PaymentMethod method,
                  Methods.NextAction nextAction, String refundRoute) {
    }

    /** Builds the intent and says what the payer does next. Nothing is stored in this station (challenge 1 stores it). */
    @PostMapping("/payment-intents")
    @ResponseStatus(HttpStatus.CREATED)
    Intent create(@Valid @RequestBody IntentRequest r) {
        if (r.method() instanceof PaymentMethod.NetBanking(String bank) && !BANKS.contains(bank)) {
            ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_CONTENT,
                    "Net banking with bank " + bank + " is not available. Available: " + String.join(", ", BANKS.stream().sorted().toList()) + ".");
            p.setTitle("Bank not available");
            throw new ErrorResponseException(HttpStatus.UNPROCESSABLE_CONTENT, p, null);
        }
        String amount = "Rs " + r.amountPaise() / 100 + "." + String.format("%02d", r.amountPaise() % 100);
        return new Intent("pi_" + UUID.randomUUID().toString().replace("-", ""), r.orderId(), r.amountPaise(), "REQUIRES_ACTION",
                r.method(), Methods.nextAction(r.method(), amount), Methods.refundRoute(r.method()));
    }
}

src/main/java/com/paysetu/payments/PaymentMethod.java

Does
The sealed interface and its four records, with the JSON type names.
Why
"Exactly one of" written as a type: impossible states cannot be built.
Without it
One class with four nullable fields.
  • @JsonTypeInfo and @JsonSubTypes map "type" to a record.
  • Compact constructors normalise UPI IDs and bank codes with Locale.ROOT.
  • WRITE_ONLY keeps the token and mobile out of responses.
package com.paysetu.payments;

import com.fasterxml.jackson.annotation.JsonProperty;
import com.fasterxml.jackson.annotation.JsonSubTypes;
import com.fasterxml.jackson.annotation.JsonTypeInfo;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;

import java.util.Locale;

/**
 * Exactly one of four ways to pay. "sealed ... permits" closes the list: a switch over PaymentMethod with no default
 * must handle every record, and adding a fifth method is a compile error everywhere one is forgotten.
 * JSON carries a "type" field that picks the record; each record has only the fields its method needs.
 */
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({
        @JsonSubTypes.Type(value = PaymentMethod.Upi.class, name = "UPI"),
        @JsonSubTypes.Type(value = PaymentMethod.Card.class, name = "CARD"),
        @JsonSubTypes.Type(value = PaymentMethod.NetBanking.class, name = "NET_BANKING"),
        @JsonSubTypes.Type(value = PaymentMethod.Wallet.class, name = "WALLET")})
sealed interface PaymentMethod permits PaymentMethod.Upi, PaymentMethod.Card, PaymentMethod.NetBanking, PaymentMethod.Wallet {

    /** A UPI ID such as asha@okaxis, stored lower-case. */
    record Upi(@NotNull @Pattern(regexp = "[A-Za-z0-9._-]{2,64}@[A-Za-z][A-Za-z0-9]{1,63}", message = "must be a UPI ID like name@bank") String vpa)
            implements PaymentMethod {
        public Upi {
            vpa = vpa == null ? null : vpa.toLowerCase(Locale.ROOT);
        }
    }

    /**
     * A saved card, as a token from the (simulated) card network plus what may be shown: network and last 4 digits.
     * The full card number never reaches this API, and the token is accepted but never written back out.
     */
    record Card(@NotNull Network network,
                @NotNull @Pattern(regexp = "\\d{4}", message = "must be the last 4 digits") String last4,
                @NotNull @Pattern(regexp = "tok_[A-Za-z0-9]{8,64}", message = "must be a card token") @JsonProperty(access = JsonProperty.Access.WRITE_ONLY) String token)
            implements PaymentMethod {
        enum Network { VISA, MASTERCARD, RUPAY }
    }

    /** Net banking at a bank, by the 4-letter bank code that starts its IFSC codes (HDFC, SBIN...), stored upper-case. */
    record NetBanking(@NotNull @Pattern(regexp = "[A-Za-z]{4}", message = "must be a 4-letter bank code") String bankCode)
            implements PaymentMethod {
        public NetBanking {
            bankCode = bankCode == null ? null : bankCode.toUpperCase(Locale.ROOT);
        }
    }

    /** The Paysetu wallet of a mobile number. Responses show the number masked. */
    record Wallet(@NotNull @Pattern(regexp = "[6-9]\\d{9}", message = "must be a 10-digit Indian mobile number")
                  @JsonProperty(access = JsonProperty.Access.WRITE_ONLY) String mobile)
            implements PaymentMethod {
        @JsonProperty("maskedMobile")
        String maskedMobile() {
            return mobile.substring(0, 2) + "******" + mobile.substring(8);
        }
    }
}

src/main/java/com/paysetu/payments/Methods.java

Does
Next action and refund route: one switch each, no default.
Why
Record patterns unpack fields in the case; the compiler checks every method is handled.
Without it
The trap: a refund chain with no wallet branch.
package com.paysetu.payments;

import com.paysetu.payments.PaymentMethod.Card;
import com.paysetu.payments.PaymentMethod.NetBanking;
import com.paysetu.payments.PaymentMethod.Upi;
import com.paysetu.payments.PaymentMethod.Wallet;

/**
 * Everything that differs by payment method, as switches over the sealed interface. No default branch on purpose:
 * the compiler proves each switch handles every method. Simulated: no UPI app, bank or card network is contacted.
 */
final class Methods {

    record NextAction(String type, String detail) {
    }

    private Methods() {
    }

    static NextAction nextAction(PaymentMethod method, String amount) {
        return switch (method) {
            case Upi(String vpa) -> new NextAction("APPROVE_IN_UPI_APP",
                    "Approve " + amount + " to Paysetu in the UPI app linked to " + vpa + ".");
            case Card(Card.Network network, String last4, String token) -> new NextAction("AUTHENTICATE_CARD",
                    "Enter the one-time password from your bank for the " + network + " card ending " + last4 + ".");
            case NetBanking(String bankCode) -> new NextAction("REDIRECT_TO_BANK",
                    "/simulated-banks/" + bankCode + "/login");
            case Wallet w -> new NextAction("CONFIRM_WALLET_DEBIT",
                    "Confirm the " + amount + " debit in the Paysetu wallet of " + w.maskedMobile() + ".");
        };
    }

    /** Where a refund of this payment goes. The old code's version of this forgot wallets. */
    static String refundRoute(PaymentMethod method) {
        return switch (method) {
            case Upi(String vpa) -> "Back to the bank account behind the UPI ID " + vpa + ".";
            case Card(Card.Network network, String last4, String token) -> "Back to the " + network + " card ending " + last4 + ".";
            case NetBanking(String bankCode) -> "Back to the account at bank " + bankCode + " it was paid from.";
            case Wallet w -> "Back to the Paysetu wallet of " + w.maskedMobile() + ".";
        };
    }
}

Builds a placeholder of every permitted record by reflection, so a method added later is tested without editing this file.

package com.paysetu.payments;

import com.fasterxml.jackson.annotation.JsonSubTypes;
import org.junit.jupiter.api.Test;

import java.lang.reflect.RecordComponent;
import java.util.Arrays;
import java.util.Set;
import java.util.stream.Collectors;

import static org.assertj.core.api.Assertions.assertThat;

/**
 * Every permitted payment method, found by reflection, so a method added later is covered without editing this test:
 * it can be sent as JSON, and it has a next action and a refund route.
 */
class EveryMethodTest {

    @Test
    void paymentMethodIsSealed() {
        assertThat(PaymentMethod.class.isSealed()).isTrue();
    }

    @Test
    void everyMethodCanArriveAsJson() {
        Set<Class<?>> registered = Arrays.stream(PaymentMethod.class.getAnnotation(JsonSubTypes.class).value())
                .map(JsonSubTypes.Type::value).collect(Collectors.toSet());
        assertThat(registered).containsExactlyInAnyOrder(PaymentMethod.class.getPermittedSubclasses());
    }

    @Test
    void everyMethodHasANextActionAndARefundRoute() throws Exception {
        for (Class<?> type : PaymentMethod.class.getPermittedSubclasses()) {
            PaymentMethod method = sample(type);
            assertThat(Methods.nextAction(method, "Rs 1.00").detail()).as(type.getSimpleName()).isNotBlank();
            assertThat(Methods.refundRoute(method)).as(type.getSimpleName()).isNotBlank();
        }
    }

    /** A record with placeholder values: "9876543210" for text, the first constant of an enum, 1 for numbers. */
    static PaymentMethod sample(Class<?> type) throws Exception {
        RecordComponent[] components = type.getRecordComponents();
        Object[] args = Arrays.stream(components).map(c -> {
            Class<?> t = c.getType();
            if (t.isEnum()) return t.getEnumConstants()[0];
            if (t == String.class) return "9876543210";
            if (t == long.class || t == Long.class) return 1L;
            return 1;
        }).toArray();
        return (PaymentMethod) type.getDeclaredConstructor(Arrays.stream(components).map(RecordComponent::getType).toArray(Class[]::new))
                .newInstance(args);
    }
}

package com.paysetu.payments;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.ErrorResponseException;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

import java.net.URI;
import java.util.Map;
import java.util.Set;
import java.util.UUID;
import java.util.concurrent.ConcurrentHashMap;

@RestController
class PaymentIntentController {

    /** Banks offered for net banking in this demo. */
    static final Set<String> BANKS = Set.of("HDFC", "ICIC", "SBIN", "UTIB", "KKBK");

    record IntentRequest(@NotNull @Pattern(regexp = "[A-Za-z0-9_-]{1,40}") String orderId,
                         @NotNull @Min(100) @Max(value = 10_000_000, message = "must be at most Rs 1,00,000 (a demo rule)") Long amountPaise,
                         @NotNull @Valid PaymentMethod method) {
    }

    record Intent(String id, String orderId, long amountPaise, String status, PaymentMethod method,
                  Methods.NextAction nextAction, String refundRoute) {
    }

    /** Challenge 1: intents kept in memory, so they can be read back. Gone when the app stops. */
    private final Map<String, Intent> intents = new ConcurrentHashMap<>();

    /** Builds the intent, keeps it, and says what the payer does next. */
    @PostMapping("/payment-intents")
    ResponseEntity<Intent> create(@Valid @RequestBody IntentRequest r) {
        if (r.method() instanceof PaymentMethod.NetBanking(String bank) && !BANKS.contains(bank)) {
            ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_CONTENT,
                    "Net banking with bank " + bank + " is not available. Available: " + String.join(", ", BANKS.stream().sorted().toList()) + ".");
            p.setTitle("Bank not available");
            throw new ErrorResponseException(HttpStatus.UNPROCESSABLE_CONTENT, p, null);
        }
        String amount = "Rs " + r.amountPaise() / 100 + "." + String.format("%02d", r.amountPaise() % 100);
        Intent intent = new Intent("pi_" + UUID.randomUUID().toString().replace("-", ""), r.orderId(), r.amountPaise(), "REQUIRES_ACTION",
                r.method(), Methods.nextAction(r.method(), amount), Methods.refundRoute(r.method()));
        intents.put(intent.id(), intent);
        return ResponseEntity.created(URI.create("/payment-intents/" + intent.id())).body(intent);
    }

    @GetMapping("/payment-intents/{id}")
    Intent read(@PathVariable String id) {
        Intent intent = intents.get(id);
        if (intent == null) {
            ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, "No payment intent has this id.");
            p.setTitle("Payment intent not found");
            throw new ErrorResponseException(HttpStatus.NOT_FOUND, p, null);
        }
        return intent;
    }
}

package com.paysetu.payments;

import com.fasterxml.jackson.annotation.JsonProperty;
import com.fasterxml.jackson.annotation.JsonSubTypes;
import com.fasterxml.jackson.annotation.JsonTypeInfo;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;

import java.util.Locale;

/**
 * Exactly one of four ways to pay. "sealed ... permits" closes the list: a switch over PaymentMethod with no default
 * must handle every record, and adding a fifth method is a compile error everywhere one is forgotten.
 * JSON carries a "type" field that picks the record; each record has only the fields its method needs.
 */
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({
        @JsonSubTypes.Type(value = PaymentMethod.Upi.class, name = "UPI"),
        @JsonSubTypes.Type(value = PaymentMethod.Card.class, name = "CARD"),
        @JsonSubTypes.Type(value = PaymentMethod.NetBanking.class, name = "NET_BANKING"),
        @JsonSubTypes.Type(value = PaymentMethod.Wallet.class, name = "WALLET"),
        @JsonSubTypes.Type(value = PaymentMethod.PayLater.class, name = "PAY_LATER")})
sealed interface PaymentMethod
        permits PaymentMethod.Upi, PaymentMethod.Card, PaymentMethod.NetBanking, PaymentMethod.Wallet, PaymentMethod.PayLater {

    /** A UPI ID such as asha@okaxis, stored lower-case. */
    record Upi(@NotNull @Pattern(regexp = "[A-Za-z0-9._-]{2,64}@[A-Za-z][A-Za-z0-9]{1,63}", message = "must be a UPI ID like name@bank") String vpa)
            implements PaymentMethod {
        public Upi {
            vpa = vpa == null ? null : vpa.toLowerCase(Locale.ROOT);
        }
    }

    /**
     * A saved card, as a token from the (simulated) card network plus what may be shown: network and last 4 digits.
     * The full card number never reaches this API, and the token is accepted but never written back out.
     */
    record Card(@NotNull Network network,
                @NotNull @Pattern(regexp = "\\d{4}", message = "must be the last 4 digits") String last4,
                @NotNull @Pattern(regexp = "tok_[A-Za-z0-9]{8,64}", message = "must be a card token") @JsonProperty(access = JsonProperty.Access.WRITE_ONLY) String token)
            implements PaymentMethod {
        enum Network { VISA, MASTERCARD, RUPAY }
    }

    /** Net banking at a bank, by the 4-letter bank code that starts its IFSC codes (HDFC, SBIN...), stored upper-case. */
    record NetBanking(@NotNull @Pattern(regexp = "[A-Za-z]{4}", message = "must be a 4-letter bank code") String bankCode)
            implements PaymentMethod {
        public NetBanking {
            bankCode = bankCode == null ? null : bankCode.toUpperCase(Locale.ROOT);
        }
    }

    /** The Paysetu wallet of a mobile number. Responses show the number masked. */
    record Wallet(@NotNull @Pattern(regexp = "[6-9]\\d{9}", message = "must be a 10-digit Indian mobile number")
                  @JsonProperty(access = JsonProperty.Access.WRITE_ONLY) String mobile)
            implements PaymentMethod {
        @JsonProperty("maskedMobile")
        String maskedMobile() {
            return mobile.substring(0, 2) + "******" + mobile.substring(8);
        }
    }

    /** Challenge 2: Paysetu Pay Later (fictional), by mobile number, shown masked. */
    record PayLater(@NotNull @Pattern(regexp = "[6-9]\\d{9}", message = "must be a 10-digit Indian mobile number")
                    @JsonProperty(access = JsonProperty.Access.WRITE_ONLY) String mobile)
            implements PaymentMethod {
        @JsonProperty("maskedMobile")
        String maskedMobile() {
            return mobile.substring(0, 2) + "******" + mobile.substring(8);
        }
    }
}

challenge/solution/Methods.java

package com.paysetu.payments;

import com.paysetu.payments.PaymentMethod.Card;
import com.paysetu.payments.PaymentMethod.NetBanking;
import com.paysetu.payments.PaymentMethod.PayLater;
import com.paysetu.payments.PaymentMethod.Upi;
import com.paysetu.payments.PaymentMethod.Wallet;

/**
 * Everything that differs by payment method, as switches over the sealed interface. No default branch on purpose:
 * the compiler proves each switch handles every method. Simulated: no UPI app, bank or card network is contacted.
 */
final class Methods {

    record NextAction(String type, String detail) {
    }

    private Methods() {
    }

    static NextAction nextAction(PaymentMethod method, String amount) {
        return switch (method) {
            case Upi(String vpa) -> new NextAction("APPROVE_IN_UPI_APP",
                    "Approve " + amount + " to Paysetu in the UPI app linked to " + vpa + ".");
            case Card(Card.Network network, String last4, String token) -> new NextAction("AUTHENTICATE_CARD",
                    "Enter the one-time password from your bank for the " + network + " card ending " + last4 + ".");
            case NetBanking(String bankCode) -> new NextAction("REDIRECT_TO_BANK",
                    "/simulated-banks/" + bankCode + "/login");
            case Wallet w -> new NextAction("CONFIRM_WALLET_DEBIT",
                    "Confirm the " + amount + " debit in the Paysetu wallet of " + w.maskedMobile() + ".");
            case PayLater p -> new NextAction("APPROVE_PAY_LATER",
                    "Approve " + amount + " on Paysetu Pay Later with the one-time password sent to " + p.maskedMobile() + ".");
        };
    }

    /** Where a refund of this payment goes. The old code's version of this forgot wallets. */
    static String refundRoute(PaymentMethod method) {
        return switch (method) {
            case Upi(String vpa) -> "Back to the bank account behind the UPI ID " + vpa + ".";
            case Card(Card.Network network, String last4, String token) -> "Back to the " + network + " card ending " + last4 + ".";
            case NetBanking(String bankCode) -> "Back to the account at bank " + bankCode + " it was paid from.";
            case Wallet w -> "Back to the Paysetu wallet of " + w.maskedMobile() + ".";
            case PayLater p -> "Back to the Paysetu Pay Later account of " + p.maskedMobile() + ", lowering what is due.";
        };
    }
}

Challenge 3 · design on paper, no code

Switches or methods on the records?

This station keeps nextAction and refundRoute as switches in one class. They could instead be methods on each record. With twelve methods and six operations, which is easier to change when a method is added, and which when an operation is added? Where would you want the compiler to help?

Belongs in this tab

  • 9. Design alternatives and trade-offs
  • 12. Database design (none in this station)

Short at Foundations: the choices that matter here.

Implementation approach

  1. Write the trap test: the old refund chain returns null for a wallet.
  2. Write the sealed interface and one record per method, with their own validation.
  3. Map JSON type to records; refuse unknown fields.
  4. Write the switches without default; check by reflection that every method is reachable and handled.

ApproachWhat it costsVerdict
Sealed interface + records + switchesA switch to update per operation when a method is added; the compiler finds them all.Chosen
One class with nullable fieldsImpossible states (UPI and card at once); every new method is a hunt.Wrong

Card data
In India, RBI's card-on-file tokenisation rules stop merchants from storing card numbers. This API accepts only a token and what may be displayed, and refuses a full number.
Privacy
Mobile numbers and tokens are write-only. Logs need the same care: never log the request body as-is.
Evolution
A new method changes the API: old clients that do not know PAY_LATER must still read responses. Document new type values before shipping them.
Real gateways
UPI, cards and net banking each have their own flows, timeouts and failure states. This station models only the first step.

Interview takeaways

What does a sealed interface give you?

A closed list of implementations, known to the compiler. A switch over it can be exhaustive without a default, so adding an implementation makes every incomplete switch a compile error.

Why no default branch?

A default branch makes an incomplete switch compile. Without it, the compiler tells you every place a new case must be handled.

What is a record pattern?

case Upi(String vpa) -> matches a Upi and binds its component in one step, instead of a cast and a getter.

How do you read polymorphic JSON safely?

A type property mapped to known subtypes, so an unknown type fails, and fail-on-unknown-properties, so fields from another type are refused instead of ignored.

How do you test every subtype without listing them?

Class.getPermittedSubclasses() gives the list at runtime; build a placeholder of each and check the behaviour, so a new subtype is covered automatically.

No reviewer view for this station

This Foundations station has no flawed version to review. Use this checklist on any "one of several kinds" code:

  • Can an object be two kinds at once, or none?
  • Does any switch or if-chain over the kinds have a default that hides a missing case?
  • Can every kind arrive from JSON, and are other kinds' fields refused?
  • Is any secret field echoed back in a response or a log?
