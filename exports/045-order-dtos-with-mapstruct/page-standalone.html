The problem in real life

  1. 600 lines of copying

    Tiffino's code copied fields between entities and API objects by hand: name to name, phone to phone, for every class.

  2. A new field, half added

    In March, "delivery instructions" was added to the table, the entity, the request and the response. Nobody added it to the copying code. It compiled, tests passed, and every "ring twice, baby sleeping" went nowhere.

  3. The fix

    Let MapStruct write the copying code, and make the build fail when any field is left unmapped without saying why.

A forgotten field should fail the build, not the customer's order.

What are we building?

POST /orders takes an order with an address, lines and delivery instructions; GET /orders/{id} returns it, phone masked, totals computed. Every field travels both ways.

An everyday analogy

A printed form with numbered boxes and a checker who refuses any form with an empty box, unless it is stamped "not needed". A clerk copying by hand skips a box now and then; the checker never does.

How it works in 4 steps

  1. You declare the mappings as an interface, with the few special rules.
  2. At compile time, MapStruct writes the code, field by field.
  3. Any target field nobody fills, and nobody marked as ignored, stops the build.
  4. At runtime, the generated code is plain Java: no reflection, no surprises.
Check yourself: why do id, status and totalPaise say ignore = true?

They must not come from the client: the database assigns the id, the service sets the status and computes the total. "Ignore" is a written decision; forgetting is not, and the build refuses it.

What this station is not

  • No order workflow. Orders stay PLACED.
  • No payment. A total, not a charge.
  • No editing. Changing lines is station 047.

Business problem

Tiffino (a fictional food delivery brand) has 600 lines of hand-written mapping between entities and DTOs; a field added to one was silently missed in the other.

Acceptance criteria

  1. Given an order with delivery instructions, then 201 and the same instructions in the response and on GET.
  2. Given 2 paneer thalis at ₹249 and 1 chaas at ₹49, then line totals ₹498 and ₹49, order total ₹547.
  3. Given any response, then the phone shows only its last 4 digits.
  4. Given a mapper that leaves a field unmapped, then the build fails, naming the field.
  5. Given a 5-digit PIN, quantity 0, a bad phone, no lines, or a totalPaise sent by the client, then 400; an unknown order, 404.

Requirements

  • Mapping is generated by MapStruct with unmappedTargetPolicy = ERROR.
  • Fields the client must not set are ignored explicitly, with a reason.
  • Totals are computed on the server; money in integer paise.
  • An order and its lines are saved together, or not at all.

Learning objectives

  • Keep entities and DTOs apart, and map between them.
  • Write MapStruct mappers with nested, list and custom mappings.
  • Use compile-time unmapped-field checks, and know their blind spot.
  • Map a bidirectional parent–child relation correctly.

The trap

Plausible but wrong

Hand-written mapping that silently skips a newly added field.

The old mapper, kept in the tests, drops the delivery instructions on the way in and on the way out. MapStruct carries them both ways.

The last two tests run the Java compiler with the MapStruct processor, on a tiny mapper each. A mapper that misses a field fails to compile, naming it. A setter that is not public compiles with no error and is never called. That second case is how this station was first built: MapStruct filled only the list of lines, and the ERROR policy did not fire, because it only checks setters it can see.

While building, each part was undone once. Not linking lines to their order turned 4 tests red, ignoring the instructions on purpose 2, and dropping the phone mask 1. Leaving out the totalPaise decision made the project fail to compile.

class OrderController {

        this.service = service;

        });
    }
}

package com.tiffino.ordering;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.Optional;

@Service
class OrderService {

    private final OrderRepository orders;
    private final OrderMapper mapper;

    OrderService(OrderRepository orders, OrderMapper mapper) {
        this.orders = orders;
        this.mapper = mapper;
    }

    /** Records an order (a demo record; no kitchen, no payment). The total is computed here, from the lines. */
    @Transactional
    OrderDtos.OrderResponse place(OrderDtos.CreateOrderRequest request) {
        Order order = mapper.toEntity(request);
        order.setStatus("PLACED");
        order.setTotalPaise(order.getLines().stream().mapToLong(l -> Math.multiplyExact((long) l.getQuantity(), l.getUnitPricePaise())).sum());
        return mapper.toResponse(orders.save(order));
    }

    /** Mapped inside the transaction: the lines are loaded while the session is open. */
    @Transactional(readOnly = true)
    Optional<OrderDtos.OrderResponse> find(long id) {
        return orders.findById(id).map(mapper::toResponse);
    }
}

package com.tiffino.ordering;

import org.mapstruct.AfterMapping;
import org.mapstruct.Mapper;
import org.mapstruct.Mapping;
import org.mapstruct.MappingConstants;
import org.mapstruct.MappingTarget;
import org.mapstruct.Named;
import org.mapstruct.ReportingPolicy;

/**
 * MapStruct writes the implementation at compile time. unmappedTargetPolicy = ERROR is the point of this station: if
 * a field is added to an entity or a response and nobody says where it comes from (or that it is ignored on
 * purpose), the build fails, naming the field. A hand-written mapper just leaves it null.
 */
@Mapper(componentModel = MappingConstants.ComponentModel.SPRING, unmappedTargetPolicy = ReportingPolicy.ERROR)
interface OrderMapper {

    @Mapping(target = "id", ignore = true)            // the database assigns it
    @Mapping(target = "status", ignore = true)        // set by the service
    @Mapping(target = "totalPaise", ignore = true)    // computed by the service, never taken from the client
    Order toEntity(OrderDtos.CreateOrderRequest request);

    @Mapping(target = "id", ignore = true)
    @Mapping(target = "order", ignore = true)         // linked back in linkLines
    OrderLine toEntity(OrderDtos.LineRequest line);

    Address toEntity(OrderDtos.AddressDto address);

    /** Each line must point at its order, or Hibernate cannot fill order_id. */
    @AfterMapping
    default void linkLines(@MappingTarget Order order) {
        order.getLines().forEach(line -> line.setOrder(order));
    }

    @Mapping(target = "phone", source = "phone", qualifiedByName = "maskPhone")
    OrderDtos.OrderResponse toResponse(Order order);

    @Mapping(target = "linePaise", expression = "java(line.getQuantity() * line.getUnitPricePaise())")
    OrderDtos.LineResponse toResponse(OrderLine line);

    OrderDtos.AddressDto toDto(Address address);

    /** Only the last four digits leave the server. */
    @Named("maskPhone")
    static String maskPhone(String phone) {
        return "******" + phone.substring(phone.length() - 4);
    }
}

package com.tiffino.ordering;

import org.mapstruct.AfterMapping;
import org.mapstruct.Mapper;
import org.mapstruct.Mapping;
import org.mapstruct.MappingConstants;
import org.mapstruct.MappingTarget;
import org.mapstruct.Named;
import org.mapstruct.ReportingPolicy;

/**
 * MapStruct writes the implementation at compile time. unmappedTargetPolicy = ERROR is the point of this station: if
 * a field is added to an entity or a response and nobody says where it comes from (or that it is ignored on
 * purpose), the build fails, naming the field. A hand-written mapper just leaves it null.
 */
@Mapper(componentModel = MappingConstants.ComponentModel.SPRING, unmappedTargetPolicy = ReportingPolicy.ERROR)
interface OrderMapper {

    @Mapping(target = "id", ignore = true)            // the database assigns it
    @Mapping(target = "status", ignore = true)        // set by the service
    @Mapping(target = "totalPaise", ignore = true)    // computed by the service, never taken from the client
    @Mapping(target = "tipPaise", source = "tipPaise", defaultValue = "0L")   // MapStruct insists on the L for a long
    Order toEntity(OrderDtos.CreateOrderRequest request);

    @Mapping(target = "id", ignore = true)
    @Mapping(target = "order", ignore = true)         // linked back in linkLines
    OrderLine toEntity(OrderDtos.LineRequest line);

    Address toEntity(OrderDtos.AddressDto address);

    /** Each line must point at its order, or Hibernate cannot fill order_id. */
    @AfterMapping
    default void linkLines(@MappingTarget Order order) {
        order.getLines().forEach(line -> line.setOrder(order));
    }

    @Mapping(target = "phone", source = "phone", qualifiedByName = "maskPhone")
    OrderDtos.OrderResponse toResponse(Order order);

    @Mapping(target = "linePaise", expression = "java(line.getQuantity() * line.getUnitPricePaise())")
    OrderDtos.LineResponse toResponse(OrderLine line);

    OrderDtos.AddressDto toDto(Address address);

    @Mapping(target = "orderId", source = "id")
    @Mapping(target = "items", source = "lines")
    @Mapping(target = "instructions", source = "deliveryInstructions")
    OrderDtos.KitchenTicket toTicket(Order order);

    /** Used by toTicket for each line: "2 x Paneer thali". */
    default String ticketLine(OrderLine line) {
        return line.getQuantity() + " x " + line.getItem();
    }

    /** Only the last four digits leave the server. */
    @Named("maskPhone")
    static String maskPhone(String phone) {
        return "******" + phone.substring(phone.length() - 4);
    }
}

package com.tiffino.ordering;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.Optional;

@Service
class OrderService {

    private final OrderRepository orders;
    private final OrderMapper mapper;

    OrderService(OrderRepository orders, OrderMapper mapper) {
        this.orders = orders;
        this.mapper = mapper;
    }

    /** Records an order (a demo record; no kitchen, no payment). The total is computed here, from the lines. */
    @Transactional
    OrderDtos.OrderResponse place(OrderDtos.CreateOrderRequest request) {
        Order order = mapper.toEntity(request);
        order.setStatus("PLACED");
        order.setTotalPaise(order.getLines().stream().mapToLong(l -> Math.multiplyExact((long) l.getQuantity(), l.getUnitPricePaise())).sum()
                + order.getTipPaise());
        return mapper.toResponse(orders.save(order));
    }

    @Transactional(readOnly = true)
    Optional<OrderDtos.KitchenTicket> ticket(long id) {
        return orders.findById(id).map(mapper::toTicket);
    }

    /** Mapped inside the transaction: the lines are loaded while the session is open. */
    @Transactional(readOnly = true)
    Optional<OrderDtos.OrderResponse> find(long id) {
        return orders.findById(id).map(mapper::toResponse);
    }
}

When is a mapper worth it?

For a public API, a mobile app, an internal admin tool and a service-to-service event, decide between: MapStruct, hand-written mapping with a test per field, returning entities, and reusing one DTO everywhere. What does each cost when a column is added, and who notices when something is missed?

Implementation approach

  1. Write the trap test with the old mapper.
  2. Write the DTOs and the mapper interface; let the build tell you every field you have not decided.

  4. Prove the compile-time check with javac in a test, including its blind spot.

Interview takeaways

Why separate entities and DTOs?

The API is a contract with clients; the table is an implementation detail. Separating them lets either change without breaking the other, and keeps private columns private.

What does MapStruct do?

It generates mapping code at compile time from an interface. The result is plain Java, fast and debuggable, and mistakes are compile errors.

What does unmappedTargetPolicy = ERROR give you?

A build failure when a target property has no source and no explicit ignore, so a newly added field cannot be forgotten silently.

What can it not catch?

Properties it cannot see, such as fields with non-public setters, and wrong-but-present mappings (two fields of the same type swapped). Tests still matter.

How do you map a parent with a list of children in JPA?

Map the list, then set each child's back-reference to the parent (an @AfterMapping here), because the child's foreign key comes from that reference.
